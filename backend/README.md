# MeetNote API

FastAPI backend for MeetNote. This foundation serves a health check, a SQLite database session, and JWT helpers. Authentication routes are not included yet.

## Setup

From the `backend` directory:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
```

Copy the example environment file and replace the JWT secret before you use authentication:

```powershell
copy .env.example .env
```

`.env` stays on your machine. The app can start without it and uses the same defaults as `.env.example`.

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | SQLAlchemy database URL. Default is SQLite file `meetnote.db`. |
| `JWT_SECRET_KEY` | Secret used to sign access tokens. |
| `JWT_ALGORITHM` | JWT signing algorithm. Default is `HS256`. |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Access token lifetime in minutes. |
| `FRONTEND_URL` | Allowed browser origin for CORS. Default is `http://localhost:5173`. |

## Run

From the `backend` directory, with the virtual environment active:

```powershell
uvicorn app.main:app --reload --port 8000
```

On startup, SQLAlchemy creates `meetnote.db` in this directory if it does not exist. There are no tables yet.

## Check

Health:

```powershell
curl http://localhost:8000/health
```

Expected response:

```json
{"status":"ok","service":"MeetNote API"}
```

Interactive API docs: [http://localhost:8000/docs](http://localhost:8000/docs)

## Speaker diarization

Transcription still uses local faster-whisper. After a transcript is decoded, MeetNote can label each segment Speaker 1, Speaker 2, and so on. Those labels are cluster numbers for that recording, not participant names.

Diarization runs inside the existing transcription job on CPU. It uses [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) (Apache-2.0). No Hugging Face token or paid API is required. If the models are missing, or diarization fails, the transcript is still saved and those segments stay "Unknown".

Install the models once from the `backend` directory, with the virtual environment active. The download is about 35 MB: a 6 MB pyannote segmentation model (MIT) and a 28 MB English 3D-Speaker CAM++ embedding model (Apache-2.0).

```powershell
python -m app.services.diarization_service
```

The files are stored in `backend/models/diarization/` and are not committed. The first diarized meeting loads both models into the API process. Expect extra CPU time and a few hundred megabytes of memory on top of Whisper. One transcription runs at a time, same as before.

A voice is numbered by the first transcript segment it is assigned to in that pass, so the numbers have no gaps. A segment stays "Unknown" when less than 30% of it overlaps detected speech or two voices overlap it almost equally. Retranscribing can number the same person differently. Segments you have edited stay as you saved them, including the speaker label on that row.

## Meeting insights

After a transcript is saved, MeetNote fills in the Summary, Action Items, and Decisions tabs from it. No setup, model download, environment variable, or API key is needed.

This is rule-based extraction, not a generative AI model. Every summary sentence, key point, action item, and decision is a sentence taken from the transcript:

- **Summary**: up to three sentences, chosen by how many of the meeting's frequent words they contain. A sentence that states the purpose ("today we'll discuss…") goes first.
- **Key points**: up to five more high-scoring sentences, each with its transcript time.
- **Action items**: sentences that commit to work ("I'll…", "we need to…", "Priya, can you…"). The assignee is set only when the sentence names someone or the speaker label is known; "I'll…" uses the speaker label, such as "Speaker 2". The due date is set only for explicit dates such as "tomorrow", "by Friday", or "October 14". Vague dates such as "next week" stay empty.
- **Decisions**: sentences that state a decision ("we decided…", "we agreed to…", "let's go with…"). Questions, suggestions ("maybe", "should we"), and open decisions ("we haven't decided") are skipped.

Transcripts with little or no speech produce an empty result rather than invented content.

### Processing and failures

Insights are generated by the same in-process transcription worker, right after the transcript commits. Status is available from `GET /meetings/{id}/intelligence` (`pending`, `processing`, `completed`, or `failed`), and the meeting page polls it. If generation fails, the transcript is unaffected, the previous insights stay as they were, and the status shows a short error. `POST /meetings/{id}/intelligence` regenerates on demand. If the server restarts mid-run, the next startup marks that run failed; regenerate to try again.

### Edits are preserved

Generated action items and decisions have `source: "ai"`. Regenerating replaces only those rows, in one commit, so retries never duplicate them. Creating or editing an item, including ticking it complete, sets `source: "manual"`, and regeneration never deletes manual rows or re-adds the original of an edited one. An edited summary (`PUT /meetings/{id}/summary`) is kept on regeneration unless `replace_summary=true` is passed. Deleted generated items can come back on the next regeneration.

Existing SQLite databases get the new columns at startup. Rows that already existed are treated as manual.
